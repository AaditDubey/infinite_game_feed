# Infinite Games App: Phase 1 Spec (Sudoku)

Oct 17, 2026 · @Aadit Dubey

Phase 1 ships a playable Sudoku on your phone, fed by puzzle packs generated offline and verified to have exactly one solution. This file lives at `docs/phase_1.md` and is the reference Claude Code works from.

## Context and scope

The app is an infinite, swipeable feed of mini puzzle games, built for casual play first. The MVP games are Sudoku, Rectangles and Queens. Skill tests (blackjack, poker hands, chess moves) come after launch.

Phase 1 builds one game end to end: Sudoku, in two sizes, 9×9 and 6×6. Puzzles are generated and verified on a laptop, shipped inside the app as JSON packs, and played on a real phone. Visuals stay plain; polish comes later.

**Out of scope for Phase 1:** the swipe feed, other games, player ratings, accounts or any backend, analytics, crash reporting, ads, subscriptions, sound, and visual polish. If a task seems to need one of these, stop and ask.

## Puzzle pipeline

Puzzles are generated and verified on the laptop; the phone only reads finished JSON. The pipeline fails loudly rather than ship a bad puzzle.

### Generator

- **Source:** Tatham's collection as a git submodule in `pipeline/vendor/puzzles`, built with CMake. The Unix (GTK) builds accept `--generate n` followed by game parameters and print n game IDs ([man page](https://manpages.ubuntu.com/manpages/noble/man6/sgt-loopy.6.html)). On macOS his CMake builds only the Cocoa app, which has no `--generate`. So `pipeline/gen/solo_gen.c` runs the same loop as `gtk.c`'s `--generate` from the command line: `solo-gen <n> <params> <seed>`. The seed is required, because Tatham's no-op frontend always returns the same random seed. Tatham's `solosolver -g` from the same build cross-checks each puzzle's grade. Details are in `pipeline/README.md`.
- **Difficulty:** Solo grades each puzzle by the deduction techniques it needs. From Intermediate up, players must reason about sets of candidates; Unreasonable requires guessing and backtracking ([Solo docs](https://www.chiark.greenend.org.uk/~sgtatham/puzzles/doc/solo.html)). Never use Unreasonable.
- **Speed:** hard grades take more attempts to generate. On the M4, 100 Advanced 9×9 puzzles take about 3 s, but 6×6 Advanced takes about 0.5 s per puzzle (about 50 s for 100). Running bands in parallel processes helps there. Cache raw output anyway.
- **Verify before coding:** read `solo.c` and run the binary to confirm the parameter string for a 9×9 grid at each grade and the game ID format. Record both in a pytest fixture. Don't guess either. Done in Task 2: see `pipeline/README.md` and `pipeline/tests/fixtures/solo_samples.json`. The 6×6 equivalents were recorded in Task 3 in `solo_samples_2x3.json`.
- **Fallback:** if the native `solo-gen` build breaks, run Ubuntu's `sgt-puzzles` package in Docker (binary `sgt-solo`), which has the same `--generate` option.

### Difficulty bands

| Band | Solo grade | Label in the app |
| --- | --- | --- |
| 1 | Trivial | Easy |
| 2 | Basic | Medium |
| 3 | Intermediate | Hard |
| 4 | Advanced | Expert |
| 5 | Extreme | Master |

Confirmed against `solo.c` at commit `616da16`: the five grade names match. The params are `3x3dt`, `3x3db`, `3x3di`, `3x3da` and `3x3de` for 9×9, and `2x3dt` to `2x3de` for 6×6. Both sizes use the same five bands and the same app labels.

### Grid sizes

The app plays 9×9 and 6×6 Sudoku.

| Size | Solo params | Digits | Boxes | Pack file |
| --- | --- | --- | --- | --- |
| 9×9 | `3x3` | 1–9 | nine, 3 wide and 3 tall | `pack-9x9-001.json` |
| 6×6 | `2x3` | 1–6 | six, 3 wide and 2 tall | `pack-6x6-001.json` |

- Each pack holds one size and says which in its `grid` field (see Pack format). The pipeline builds one size per run.
- Same bands and labels for both sizes.
- The player doesn't choose a size. "Next puzzle" picks 9×9 or 6×6 at random within the chosen band (see Persistence for the no-repeat rule).

### Steps

1. **Generate** game IDs per band with Solo; save them to `pipeline/out/raw/` (gitignored).
2. **Parse** each game ID into a givens string with one character per cell (81 for 9×9, 36 for 6×6): row-major, `0` for an empty cell.
3. **Verify** with our own solver: no duplicate digit in any row, column or box; exactly one solution (stop searching at two); the solution is a complete valid grid that matches every given.
4. **Deduplicate** by givens string, including against packs already in `assets/`.
5. **Write** the pack, sorted by band then id. Same input must produce a byte-identical file, so `createdAt` comes from the cached raw output rather than today's date.
6. **Report** counts per band and rejects by reason. Any uniqueness failure exits non-zero: Solo guarantees uniqueness, so a failure means a parsing bug. The same goes for every other reject except a duplicate (malformed, no solution, grade mismatch and so on): the build exits non-zero and writes nothing.

Phase 1 target: 100 puzzles per band for each size, 1,000 total. They go in `assets/puzzles/sudoku/pack-9x9-001.json` (194 KB) and `pack-6x6-001.json` (134 KB). Both were built in Task 4 with zero rejects.

### Pack format

```json
{
  "schemaVersion": 1,
  "game": "sudoku",
  "packId": "sudoku-9x9-001",
  "grid": { "size": 9, "boxWidth": 3, "boxHeight": 3 },
  "createdAt": "2026-10-17",
  "generator": { "name": "tatham-solo", "version": "<puzzles git commit>" },
  "puzzles": [
    {
      "id": "sudoku-9x9-001-0001",
      "band": 1,
      "grade": "trivial",
      "givens": "530070000600195000098000060800060003400803001700020006060000280000419005000080079",
      "solution": "534678912672195348198342567859761423426853791713924856961537284287419635345286179",
      "clues": 30,
      "sourceId": "<Solo game ID>"
    }
  ]
}
```

| Field | Meaning |
| --- | --- |
| `grid` | Pack level: the shape of every puzzle in the pack. `{ "size": 9, "boxWidth": 3, "boxHeight": 3 }` or `{ "size": 6, "boxWidth": 3, "boxHeight": 2 }`. Box sides are explicit because 36 cells alone don't say which way the boxes run. |
| `id` | Permanent, and includes the size (`sudoku-9x9-001-0001`, `sudoku-6x6-001-0001`). Never changed or reused once shipped, because saved games and results reference it. |
| `band` | 1–5, from the table above. |
| `grade` | Solo's grade, lowercase. |
| `givens` | One character per cell (`size`², so 81 or 36), row-major, `0` = empty. |
| `solution` | Same length as `givens`: the unique solution. |
| `clues` | Number of non-zero givens. |
| `sourceId` | Solo's game ID, so any puzzle can be regenerated. |

The app's loader rejects a pack whose `schemaVersion` it doesn't know, or whose `grid` isn't one of the two shapes above. The sample puzzle values are illustrative.

## App behavior

Phase 1 is one screen: a Sudoku board, a number pad and a few controls. Taps must feel instant, and closing the app mid-game must lose nothing.

### Screen

- **Top bar:** band label, timer (mm:ss), mistake count, and a band picker for testing. Adaptive difficulty replaces the picker in Phase 2. There's no size picker; see Grid sizes.
- **Board:** a square grid, 9×9 or 6×6, the largest that fits between the band picker and the number pad (full width on most phones, a little smaller on short ones), with thicker lines between the boxes (3×3 on 9×9; 3 wide and 2 tall on 6×6).
- **Number pad:** digits 1 to the grid size (1–9 or 1–6). A digit's button dims once every copy of it (nine, or six) is placed correctly.
- **Toolbar:** Undo, Erase, and a Notes toggle.
- **Solved:** the number pad and toolbar give way to a panel, at the same height, with the time, the mistake count and a "Next puzzle" button. The board stays visible. There's no skip button in Phase 1; Phase 2's swipe moves on from an unsolved puzzle.

### Rules

| Action | Behavior |
| --- | --- |
| Tap a cell | Selects it. Highlights its row, column and box, plus every cell holding the same digit. |
| Tap a digit | Places it in the selected cell and clears that cell's notes, unless the cell is locked: givens and correct digits can't be replaced. If it differs from the solution, the cell turns red and mistakes go up by 1. The wrong digit stays until erased or replaced. Mistakes never end the game. |
| Correct digit placed | Removes that digit from notes in the same row, column and box. |
| Row, column or box completed | When a correct digit completes a row, column or box, its cells flash green once. One digit can complete all three at once. |
| Notes on, tap a digit | Toggles that pencil mark in the selected empty cell. |
| Erase | Clears the selected cell's digit or notes. Givens and correct digits are locked and can't be erased. |
| Undo | Reverts the last wrong digit, note or erase, back as far as the last correct digit. A correct digit is permanent, like a given, so placing one clears the undo history. The mistake count never goes down. |
| Every cell correct (81, or 36) | Puzzle solved: timer stops, input locks, results are saved. |
| App goes to background | Timer pauses; it resumes on return. Brief iOS interruptions that leave the app on screen (Control Center, Notification Center, the app switcher, an incoming-call banner) don't pause it. There's no pause button. |

### Persistence

- Save the game after every move: puzzle id, cells, notes, mistakes, elapsed time and undo history. Also save it when the app leaves the screen (the background, or iOS's brief inactive state), so the timer survives the app being killed: the iOS app switcher can close the app from the inactive state without a background event.
- On launch, resume an unsolved saved game. After a solved one, serve the next puzzle in its band; with no save, start on Easy. The splash screen stays up until the save has loaded. A save that no longer fits its puzzle (unknown id, wrong cell count, changed givens and so on) is ignored, so a bad save starts a fresh game instead of stopping the app from opening.
- Append to a results log on every solve: puzzle id, grid size, band, solved-at time, elapsed milliseconds, mistakes. Each entry is `{ outcome: 'solved', puzzleId, size, band, at, elapsedMs, mistakes }`, with `at` in milliseconds since 1970. In development builds each entry is also printed to the `npx expo start` terminal.
- From Phase 2, also log an abandon (`outcome: 'abandoned'`) when a swipe leaves a game unsolved, with elapsed time and mistakes. Phase 3's rating will use these. The band picker is only for testing, so it logs nothing.
- Next puzzle, and the no-repeat rule:
  - A puzzle counts as played only once the player solves it. A skipped or abandoned puzzle stays unplayed and can be served again.
  - "Next puzzle" picks a size at random (even odds) among the sizes that still have unplayed puzzles in the band. It then serves the next unplayed puzzle of that size, in pack order after the last puzzle it served of that band and size, wrapping around to the start. So a skipped puzzle comes back only after every other unplayed puzzle of its band and size has been served.
  - No solved puzzle repeats until every puzzle in the band, both sizes, has been solved. Then that band starts over.
  - Save the solved puzzle ids and the last puzzle served for each band and size, so the order survives a restart.
  - The random source is passed in, so tests can fix it.
- Prefix every storage key with `v1:` so the format can change later. Phase 1 uses `v1:sudoku:game`, `v1:sudoku:playHistory` and `v1:sudoku:results`.
- The results log is one JSON list, about 150 bytes per entry. Android caps one stored value at about 2 MB, so Phase 3 may need to split the log.

### Engine design

`engine.ts` holds every rule as pure functions that return a new state and never mutate. No React, no storage, no clock: callers pass in anything time-based. Selection and the timer live in the Zustand store, not the engine. Components read the store and contain no game rules.

```ts
export type Digit = 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 | 9; // 6×6 uses 1–6

export type GridSize = 6 | 9; // boxes: 3×3 on 9×9; 3 wide × 2 tall on 6×6

export interface Puzzle {
  id: string;
  band: 1 | 2 | 3 | 4 | 5;
  size: GridSize;
  givens: string;   // size² chars, '0' = empty
  solution: string; // size² chars
}

export interface CellState {
  value: Digit | null;
  given: boolean;
  notes: Digit[];   // sorted, no duplicates
  wrong: boolean;   // value differs from the solution
}

export interface CellChange {
  index: number;
  before: CellState; // the cell as it was before the move
}

export interface GameState {
  puzzle: Puzzle;
  cells: CellState[];       // size², row-major
  mistakes: number;
  history: CellChange[][];  // per move, only the cells it changed; cleared by a correct digit
  solved: boolean;
}

// createGame, placeDigit, toggleNote, erase, undo, isSolved
// highlights (selected cell, its peers, same digit) and completedDigits (for dimming the pad)
// completedUnits (the row, column and box a correct digit completed, for the green flash)
```

History keeps only the changed cells, not a copy of the whole board per move, because the game is saved after every move: a full copy is about 4 KB of JSON, so a long game would write hundreds of KB per tap.

### Quality bar

- Portrait, phones only; light theme only, with every color from `theme.ts`.
- Each cell has an accessibility label such as "Row 3, column 5, 7" or "Row 3, column 5, empty".
- No visible lag when tapping on a mid-range Android phone.

## Definition of done

Phase 1 closes when every box below is ticked on a real phone, not a simulator.

- [ ] `pack-9x9-001.json` and `pack-6x6-001.json` each hold 100 puzzles in each of bands 1–5, built by the pipeline with zero uniqueness failures.
- [ ] Rebuilding each pack from the same raw output produces an identical file.
- [ ] `uv run pytest` and `npm run check` pass.
- [ ] Engine tests cover placing, wrong digits and mistake counting, notes and note cleanup, erase, undo, locked givens and correct digits, and solve detection, on both grid sizes.
- [ ] A full 9×9 puzzle and a full 6×6 puzzle can each be played from start to solved screen on your phone.
- [ ] Killing the app mid-game and reopening it restores the board, notes, mistakes and timer.
- [ ] Solves appear in the results log with the right fields. (Abandons arrive with Phase 2's swipe.)
- [ ] No file in `assets/puzzles/` was edited by hand.

## Build order

Run each task as its own plan-mode session, and commit when it passes its checks. Tasks 1 and 2 are a good first day: task 2 decides whether the pipeline plan holds.

1. **Scaffold.** Create the Expo app with strict TypeScript, Prettier, Jest (`jest-expo`) and `npm run check`. Add `CLAUDE.md` pointing at this file. Confirm it opens in Expo Go on your phone.
2. **Tatham spike.** Add the submodule and build Solo, or use the Docker fallback. Confirm the parameter strings and game ID format, generate 5 IDs per grade, and record the findings in `pipeline/README.md` plus a pytest fixture.
3. **Solver and verification.** A Python solver that counts solutions up to 2, plus validity and solution checks. Test with known unique, non-unique and invalid grids, for 9×9 and 6×6.
4. **Pack builder.** Parse, verify, deduplicate, write deterministically, report. Build `pack-9x9-001.json` and `pack-6x6-001.json`.
5. **Types and loader.** TypeScript types matching the pack, the `schemaVersion` and `grid` checks, and next-puzzle selection by band with the random size pick, with tests.
6. **Engine.** Every rule in the Rules table, written test-first, for both sizes.
7. **Board UI.** Board, cells, number pad and toolbar for 9×9 and 6×6, with selection highlights, wired through the Zustand store.
8. **Game flow.** Mistakes, timer with background pause, solved screen, next puzzle, band picker.
9. **Persistence.** Save and resume, the results and abandon log, and the no-repeat rule.
10. **Device pass.** Play full puzzles on iPhone and Android, fix anything slow or wrong, and tick the definition of done.

If task 2 stalls, tasks 5–8 can continue on a small hand-made fixture kept in the tests folder, never in `assets/`.

## Rules for agents

The owner is new to React Native and relies on these rules to catch mistakes. Follow them on every task.

- Read this file before planning. If a request conflicts with it, stop and ask.
- Plan first, and wait for approval before writing code.
- One task per session. Nothing from the out-of-scope list without asking.
- No new dependencies without asking. Add them with `npx expo install` or `uv add`.

- Don't guess APIs. Check current docs through Context7 or the Expo MCP server, and Tatham's source for generator details.
- End each task with a plain-language explanation of any non-obvious code.
- Small commits on a feature branch with clear messages. Never commit straight to `main` or force-push.
- If this spec is wrong or missing something, say so and propose the change instead of working around it.
